## FACTS
### Netflix `VegasLimit.java` @ `414f64dd` (`updateEstimatedLimit`)
```
queueSize = ceil(limit × (1 − rtt_noload/rtt))
if (didDrop) → decrease
else if (inflight * 2 < limit) → hold ("prevent upward drift if not close to limit")
else:
  alpha=3*LOG10, beta=6*LOG10, threshold=LOG10   (shipped)
  queueSize <= threshold → limit + beta        (aggressive increase)
  queueSize <  alpha     → limit + LOG10       (slow increase)
  queueSize >  beta      → limit - LOG10       (decrease)
  else                   → hold
newLimit = clamp(1, maxLimit)
newLimit = (1-smoothing)*limit + smoothing*newLimit
```
- Shipped bands (3/6/1 at limits 1-99) overshoot everywhere (cap-1 peak 10); Javadoc
  states proportional intent `alpha=Max(3,10%)`, `beta=Max(6,20%)`. Follow intent.
- `VegasLimitTest.java create()`: initialLimit 10, maxConcurrency 20, smoothing 1.0,
  alpha 3, beta 6. Aggressive increase `+beta`, decrease `-LOG10`, hold in sweet spot.
- Netflix overshoots by design (increase aggressively when no queue, pull back when
  queue > beta); relies on initialLimit near optimum.

### DEAD-ZONE FIX (2026-10-26, two-part)
**Problem:** capacity-4 regressed to avg 5.49/peak 6 after the 1.2 dead-zone was added
to stop the jittery-contention spiral. Trace showed the controller oscillated 5↔6:
at limit 5 the ratio is a *stable* 1.179 — real mild queuing one step above the
capacity-4 optimum — but the 1.2 dead-zone masked it (queueSize=0, hasQueuing=false),
so the controller crept up to 6 instead of pulling back to 4.

**Fix part 1 — dead-zone 1.2 → 1.15** (`MIN_QUEUING_RATIO`): 1.2 sat ABOVE the
capacity-4 overshoot ratio (1.179). Lowering to 1.15 (still above jitter average
~1.1, below the mild-queuing signal 1.179) lets limit 5 correctly detect queuing
and decrease to 4. Verified the jittery-contention resource still converges near
its optimum (avg 7.3-7.9 across seeds on optimal=8) without collapsing to 1,
because its jitter spikes are transient (recover via slow-increase on low-ratio
probes) whereas capacity-4's overshoot ratio is stable.

**Fix part 2 — `settled` gates BOTH increase branches**: even at the optimum
(limit 4, ratio 1.0) the slow-increase branch (`queueSize < alpha && !hasQueuing`)
still fired on every probe because `settled` only gated the aggressive branch. So
the controller kept creeping up 4→5→6→5→4... (avg 4.99). Gating the slow-increase
branch with `!settled` too makes a settled controller HOLD at the sweet spot until
the next re-probe (which clears `settled`), giving avg 4.04.

### REAL-CONTENTION COLLAPSE + RECOVERABLE-BASELINE FIX (2026-10-26)
**Problem:** driven through sway's real async scheduler on `createContentionResource(8)`,
the strict-minimum `minLatency` baseline (Netflix `rtt_noload`) sampled the absolute low
tail of the 20%-jitter distribution (~9.86) while the EMA tracked the mean (~11.66) —
a ~1.5-1.8ms gap that read as ratio 1.15-1.18 at the *optimum*, indistinguishable from
real mild overshoot (capacity-4@5 ratio 1.179). After the overshoot to ~11 set
`settled=true`, the residual inflated EMA kept `hasQueuing` true on every probe, cascading
11→…→1; slow penalized tasks completing after pull-back kept the EMA elevated even at c=1,
and the anti-drift guard (`inflight=0`) pinned it there. 43/62 probes held by the guard;
avg collapsed to ~2.9. The deterministic sim had NOT reproduced this (its `inflight`
stayed saturated → guard never fired; its minLatency floor sampled differently).

**Fix — recoverable low-percentile baseline** (`BASELINE_WINDOW_SIZE=64`, `BASELINE_PERCENTILE=0.25`):
`minLatency` is now the P25 of a rolling 64-sample window instead of a strict monotonic
minimum. On deterministic resources (no jitter) the percentile == the exact floor, so
cap-1/4/16 settle identically (still pass). On jittery/overshoot resources the baseline
recovers once the window flushes penalty samples, so a stale spike no longer leaves a
permanently inflated latency ratio.

**Verified (real contention optimal=8, 500 tasks):** avg **8.096**, peak 12, duration 763ms.
Trajectory: ramps 4→12, overshoot penalty pulls back 12→11→10→9, then at c=8 the ratio
drops to ~1.11 (below dead-zone 1.15) and **holds at 8 for 412/500 completions** — NO
collapse to 1. Full `npm run test` = 64 tests / 5 files pass.
